### Задание 1. СУБД

Кейс

Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

1.1.* Хеширование стало занимать длительно время, какое API можно использовать для ускорения работы?

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.

1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это реализовать?

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.

1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД логистов?

1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?

Ответ.

1.1 Лучший тип СУБД:

    - для оперативного учёта бюджетов – реляционная SQL-СУБД (PostgreSQL, Oracle, MS SQL и т.п.);

    - для тяжёлых отчётов и аналитики – поверх неё можно сделать аналитическое хранилище (OLAP / колонночная БД).

    Почему:

    - SQL даёт строгую схему, ключи, ограничения, транзакции → целостность и корректность финансовых данных;

    - удобно строить финансовые отчёты и агрегаты (SUM, AVG, GROUP BY, JOIN);

    - для прогнозов рисков данные удобно выгружать в системы аналитики/ML.

1.1* Если речь о тяжёлом хешировании больших объёмов данных (например, для проверки целостности/шифрования), то его можно распараллелить на видеокарте.

1.2 Лендинги (посадочные страницы):

    - NoSQL документная БД (MongoDB и аналоги):

        - легко хранить разные формы в виде документов;

        - простое горизонтальное масштабирование при большом трафике.

CRM (маркетологи и продажники):

    - классическая реляционную SQL-СУБД (MySQL, PostgreSQL):

        - удобные связи между таблицами (клиент — сделки — платежи и т.д.);

        - удобные отчёты, сегментация, фильтры.

1.2* Да, можно:

Взять PostgreSQL (или другую современную SQL-СУБД), где:

    - CRM хранить в нормальных реляционных таблицах,

    - данные с лендингов — в JSON/JSONB-колонках, чтобы схема была гибкой.

1.3 Реляционная SQL-СУБД:

    - таблица sections (разделы),

    - таблица documents (документы, ссылки на файлы, версии),

    - связи по подразделениям компании и т.п.

1.3* Если уже есть центральная реляционная БД (например, та же PostgreSQL для бюджетирования/CRM), то для базы знаний можно:

    - создать отдельную схему (например, kb или quality);

    - завести в ней свои таблицы: разделы, документы, версии, права доступа.

Плюсы:

    - не плодим новые СУБД;

    - проще администрировать и бэкапить;

    - можно использовать общие механизмы авторизации/ролей.

1.4 Графовая СУБД (например, Neo4j и аналоги), так как оптимизирована именно под запросы по связям:

    - поиск кратчайшего пути,

    - ближайших точек,

    - всех маршрутов между двумя объектами.

Такие запросы в графовой БД обычно гораздо проще и быстрее, чем в обычной реляционной, когда связей очень много и они глубокие.

1.4* У отдела закупок обычно свои задачи поставщики, договоры, цены, заявки, счета, статусы - это данные, которые, как правило, хорошо ложатся в реляционную модель.

Варианты:

Разделение по типу данных (рекомендуется):

    - Логистика: графовая СУБД для маршрутов и структуры сети.

    - Закупки: реляционная СУБД для поставщиков, договоров и заказов.

Связь между ними через сервисы/интеграцию (например, заявки из закупок → данные о маршрутах из логистики).

Подключить закупки к графовой БД – можно, но будет неудобно - финансовые/договорные данные в графе вести сложнее и менее привычно, чем в таблицах.

Лучше дать логистике графовую СУБД, а закупкам — свою реляционную, связав их на уровне приложений/сервисов или интеграции.

1.5* У отдела закупок обычно свои задачи:

поставщики, договоры, цены, заявки, счета, статусы.

это данные, которые, как правило, хорошо ложатся в реляционную модель.

Варианты:

Разделение по типу данных (рекомендуется):

Логистика: графовая СУБД для маршрутов и структуры сети.

Закупки: реляционная СУБД для поставщиков, договоров и заказов.

Связь между ними через сервисы/интеграцию (например, заявки из закупок → данные о маршрутах из логистики).

Подключить закупки к графовой БД – можно, но будет неудобно:

финансовые/договорные данные в графе вести сложнее и менее привычно, чем в таблицах.

Поэтому внятный ответ:

Лучше дать логистике графовую СУБД, а закупкам — свою реляционную, связав их на уровне приложений/сервисов или интеграции.

1.5.* Можно ли всё решить одной СУБД?

Все задачи можно решить на одной мощной реляционной SQL-СУБД (например, PostgreSQL), если:

- бюджетирование и CRM – обычные таблицы;

- база знаний – отдельная схема с таблицами документов/разделов;

- данные лендингов – JSON/JSONB в тех же таблицах или отдельных;

- логистику (маршруты) представить через таблицы и связи (adjacency list, матрицы расстояний, возможно с расширением GIS).

Но специализированные СУБД (графовые, колоночные, NoSQL) решат часть задач проще и быстрее, чем «одна универсальная».

Вывод: «Можно сделать всё на одной реляционной СУБД, но эффективнее использовать разные типы под разные задачи».

### Задание 2. Транзакции

2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы транзакция завершилась успешно. Ориентируйтесь на шесть действий.

2.1.* Какие действия должны произойти, если пополнение счёта телефона происходило бы через автоплатёж?

Приведите ответ в свободной форме.

Ответ.

Пользователь пополняет баланс счёта телефона.

1. Представим, что пользователь платит через банк/приложение:

    Пользователь вводит данные и отправляет платёж
    Вводит номер телефона, сумму, выбирает карту/счёт и нажимает «Оплатить». Запрос с этими данными уходит в платёжную систему.

2. Создаётся транзакция в СУБД банка
    Система начинает транзакцию (BEGIN): резервирует/блокирует нужную сумму на счёте пользователя.

3. Проверки
    Система проверяет:

        - достаточно ли средств на счёте;

        - корректен ли номер телефона;

        - доступен ли оператор связи и т.п.
    Если что-то не так — транзакция сразу откатывается (ROLLBACK).

4. Списание денег со счёта пользователя
    В БД банка выполняется UPDATE баланса счёта (уменьшается на сумму пополнения) и INSERT записи в журнал операций/платежей.

5. Зачисление денег оператору связи
    Формируется запись о платеже для оператора (либо сразу обновляется баланс лицевого счёта телефона в БД оператора, либо отправляется подтверждённый платёж в его систему).

6. Фиксация транзакции и уведомление
    Если все шаги прошли успешно, транзакция фиксируется (COMMIT):

У пользователя в банке деньги списаны, у оператора баланс телефона увеличен, пользователю отправляется квитанция/СМС.
Если на любом шаге ошибка — выполняется ROLLBACK, деньги остаются на счёте, баланс телефона не меняется.


Пополнение счёта телефона происходит через автоплатёж.

(Считаем, что один раз заранее пользователь уже настроил автоплатёж (номер телефона, сумма, порог, лимит и т.п.)).

Дальше, при срабатывании автоплатежа, происходит:

1. Система по расписанию/условию проверяет баланс телефона
    Например: раз в день или при каждом событии «баланс ниже 100 ₽».

2. Обнаружение условия автоплатежа
    Баланс ниже заданного порога — система формирует внутренний запрос на платёж (номер телефона, сумма, счёт списания).

3. Запуск транзакции автоплатежа в БД банка
    Начинается транзакция (BEGIN), берутся настройки автоплатежа, проверяются лимиты, статус автоплатежа (не отключён ли).

4. Проверки и резервирование средств
    Проверяется:

        - достаточно ли денег на счёте/карте;

        - не превышен ли дневной/месячный лимит автоплатежей;
        - при успехе — сумма резервируется.

5. Списание денег и зачисление оператору

Фиксация и уведомление пользователя
При успехе — COMMIT и отправка СМС/уведомления «Автоплатёж на ХХХ ₽ выполнен»,
при ошибке — ROLLBACK и уведомление, что автоплатёж не прошёл (например, недостаточно средств).

### Задание 3. SQL vs NoSQL

3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL.

3.1.* Какие, на ваш взгляд, преимущества у NewSQL систем перед SQL и NoSQL.

Приведите ответ в свободной форме.

Ответ.

3.1 Преимущества SQL-систем по отношению к NoSQL:
- стандартизированный язык и мощные возможности запросов (SQL)
- гарантии согласованности и ACID-транзакции
- строгая схема данных и целостность
- снижение избыточности данных за счет нормализации
- зрелость, экосистема и универсальность

3.2 NewSQL — это современный класс СУБД, который пытается объединить лучшие черты обоих миров. Они сохраняют реляционную модель и поддержку SQL, но перестраивают внутреннюю архитектуру для горизонтального масштабирования, как у NoSQL.

По сравнению с традиционными SQL-СУБД

- горизонтальное масштабирование
- высокая производительность на больших нагрузках OLTP
- отказоустойчивость и авто-перераспределение данных

По сравнению с NoSQL-системами

- сохранение SQL и реляционной модели
- полноценные ACID-транзакции и строгая согласованность
- более строгая схема (по желанию) и валидация на уровне БД


### Задание 4. Кластеры

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.

На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?

Приведите ответ в свободной форме.

Ответ.

Мы выбираем такую СУБД, которая хорошо работает в кластере и умеет быстро сканировать и обрабатывать большие объёмы данных параллельно (часто это колоночные/аналитические СУБД или хранилище в распределённой файловой системе + вычислительный фреймворк).

Для таких условий (1000 машин, большие данные и много однотипных вычислений) лучше всего себя показывает data-parallel модель: данные делятся на независимые партиции, и одна и та же функция применяется к каждой партиции параллельно («вычисления едут к данным»).
